# Этап 3: неизменяемые архивные снимки

План исполнения через TDD; применяются superpowers:executing-plans и verification-before-completion. Контракт утверждён тимлидом. Новые зависимости не нужны.

**Цель:** сохранить точный JSON отчёта и CSV один раз и возвращать эти байты без пересчёта после любых новых доставок или изменения кода проектора.

**Архитектура:** новая таблица `snapshots` в существующей SQLite/PostgreSQL базе. Один захват квитанций → проектор → однократная сериализация двух артефактов → одна атомарная INSERT. UPDATE/DELETE запрещены отдельными триггерами. Существующая таблица квитанций не перестраивается.

## Формат и интерфейсы

Поля таблицы: UUID `id`, UTC `created_at`, `format_version=snapshot-v1`, `policy_version`, `parameters_json`, `semantic_fingerprint`, `report_json` BLOB/BYTEA, `ledger_csv` BLOB/BYTEA, `report_sha256`, `csv_sha256`.

- JSON: нормализованный порядок ключей, UTF-8 без BOM, сериализация один раз.
- CSV: UTF-8 с BOM, строки CRLF от csv.writer; хеш включает BOM и все байты.
- SHA-256 относится к точным сохранённым байтам. Существующий semantic_fingerprint имеет отдельный смысл и не подменяет эти два хеша.
- created_at — время создания архива, не дата события и не as_of.
- UUID генерируется при сохранении. Коллизия отвергается; старый снимок не обновляется.

Модуль `snapshots.py`:

- `save_snapshot(store, *, start, end, as_of=None, channel=None, category=None) -> manifest`;
- `list_snapshots(store, *, offset=0, limit=20) -> {items,total,offset,limit}`;
- `get_snapshot(store, snapshot_id) -> manifest` с проверкой целостности;
- `read_snapshot_bytes(store, snapshot_id, *, format="json") -> (manifest, bytes)`;
- `export_snapshot(store, snapshot_id, *, format, output: Path) -> manifest`.

Manifest: id, created_at, format_version, policy_version, parameters (нормализованный window), semantic_fingerprint, report_sha256, csv_sha256. Metadata-list не загружает полные артефакты. Пагинация использует существующий MAX_OFFSET, limit от 1 до 200.

CLI: `snapshot-save` с фильтрами отчёта; `snapshot-list`; `snapshot-export ID --format json|csv --output PATH`. Файл открывается `xb`: существующий файл не затрагивается. При сбое записи возможен частичный **новый** файл; команда завершится ошибкой. Это не обещание атомарного файлового экспорта.

HTTP только GET: `/api/snapshots`, `/api/snapshots/{id}`, `/api/snapshots/{id}/report`, `/api/snapshots/{id}/ledger.csv`. Артефакты возвращаются как сохранённые bytes, без повторного json.dumps, BOM или вызова проектора. Перед выдачей проверяются оба SHA-256. Заголовки: X-Snapshot-ID, X-Content-SHA256, X-Snapshot-Fingerprint. Неизвестный UUID: 404; неверный формат UUID/параметры: 400/422; нарушение целостности: 409 с русским объяснением.

## Интерфейс и границы

В панели отдельный выбор архива с UUID/created_at и видимым режимом «Архивный снимок». Показатели, графики, воронка, когорты, качество и журнал берутся из сохранённого JSON. Живые фильтры и сравнение as_of отключены; возврат к живому пересчёту — явный. CSV и JSON скачиваются из сохранённых артефактов. Живой CSV по-прежнему пересчитывается и явно отличается от архива.

Архив не содержит исходный raw-журнал: ссылки на события не являются автономным доказательством исходных доставок. Очередь качества нельзя заново запрашивать как будто она архивная; её drilldown в архивном режиме отключён. Просмотр имеющихся канонических источников, если доступен, явно обозначается как чтение текущей базы, а не архивного raw-содержимого. SHA-256 — не цифровая подпись. Администратор базы способен отключить триггеры; гарантия относится к интерфейсам приложения и обычным UPDATE/DELETE.
