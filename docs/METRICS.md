# Семантика показателей и границы воспроизведения

## Событие

Обязательные непустые строки: `event_id`, `event_type`, `occurred_at`, `user_id`, `session_id`, `rental_id`, `channel`, `category`. Максимум 200 символов на строковое поле. Неизвестные поля и повторные ключи JSON отклоняются: незаметное добавление неподдерживаемых полей не меняет контракт. Время события обязательно содержит часовой пояс и нормализуется в UTC с микросекундами.

`paid` требует `amount_cents`: целое от 1 до 1 000 000 000, не bool. Другие типы не допускают сумму. Отмена всегда полная. ID и категории регистрозависимы. Строки не обрезаются автоматически, кроме разделителей строк JSONL при чтении файла; точный JSON каждой строки сохраняется отдельно.

Вход хранилища — строка Python (`str`); CLI читает UTF-8 и удаляет только разделитель строки. В базе `stored_raw_json` содержит ASCII JSON-обёртку этой строки: она сохраняет без потерь даже NUL и одиночные Unicode-суррогаты, которые PostgreSQL TEXT не поддерживает напрямую. API возвращает декодированное `raw_json` и экранирует JSON-ответ. `raw_sha256` — SHA-256 от `raw.encode("utf-8", "surrogatepass")`; для обычной UTF-8-строки это исходные байты строки без её разделителя. Суррогаты и NUL в канонических полях запрещены и дают карантин, а не отказ всей загрузки. Некорректный `source` отклоняется до транзакции.

Эквивалентность сравнивает нормализованный объект: порядок ключей, отступы и эквивалентные временные зоны не создают конфликт. SHA-256 исходной строки и SHA-256 нормализованного объекта — разные поля с разными назначениями.

## Период и время знания

`[start,end)` применяется к времени событий; `as_of` — только к времени получения. Оплата 10 января, полученная 6 января, видна в январском отчёте со срезом знания 7 января. Такая комбинация полезна для проверки независимости осей, хотя реальный источник обычно присылает события после их совершения.

Без `as_of` используются все квитанции. Исторический импорт разрешён для лаборатории; при использовании реального источника время получения обязан назначать доверенный импортёр.

## Таблица показателей

| Поле | Формула и область |
|---|---|
| `gross_cents` | Сумма действительных оплат с событием в периоде |
| `reversed_cents` | Положительная величина полных отмен в периоде; связанная оплата может быть раньше периода |
| `net_cents` | `gross_cents - reversed_cents`; может быть отрицательным |
| `paid_rentals` | Число действительных оплат в периоде, максимум одна на `rental_id` |
| `cancelled_rentals` | Число действительных отмен в периоде, максимум одна на аренду |
| `conversion_pct` | Завершившие оплату сессии / сессии с первым действительным просмотром в периоде × 100 |
| `daily` | Группировка журнала оплат и отмен по календарной дате UTC; дни без операций отсутствуют |
| `quality` | Все квитанции до `as_of` во всей базе; период и сегмент не применяются |
| `exclusions` | Принятые, но семантически неучтённые события обработанной истории до `end` |

Канал и категория относятся к сессии. Несовпадение между её событиями — `identity_mismatch`; произвольная смена атрибуции не допускается. Воронка и число оплат имеют разные знаменатели: оплата в периоде может происходить по просмотру до начала периода.

## Когорты

Первая действительная оплата пользователя определяется по всей известной истории до `end`. В таблицу попадают пользователи, у которых эта оплата находится в периоде и соответствует выбранному сегменту. Поздняя доставка более ранней оплаты может переместить пользователя в старую когорту: это пересмотр знания, не редактирование события.

Неделя — понедельник–понедельник UTC. Н0 содержит первую оплату и служит базой 100%; на следующих неделях активность означает оплату другой аренды. При фильтре сегмента дальнейшие оплаты должны соответствовать этому же сегменту. Отмена не удаляет факт оплаченной активности.

`observed[i]`: начало недели раньше `end`. `mature[i]`: следующая неделя началась не позже `end`. Если неделя не наблюдалась, `retention[i] = null`. Неполная неделя содержит частичный результат и пунктирную маркировку. Эти флаги **не подтверждают полноту источников**: даже завершённая неделя может измениться после поздней доставки.

## Семантические исключения

- `missing_predecessor`: отсутствует обязательный предыдущий этап с не более поздним временем события.
- `identity_mismatch`: пользователь, аренда, канал или категория не согласованы с принятой цепочкой сессии; для отмены также проверяется сессия исходной оплаты.
- `duplicate_payment`: по аренде уже учтена оплата, хотя у повторного события другой ID.
- `duplicate_cancellation`: по аренде уже учтена полная отмена.
- `repeated_stage`: повтор этапа в той же сессии с новым ID.

При равном времени события этапы сортируются по порядку пути, затем по `event_id`. События с одной меткой времени допускаются. Повторный просмотр не начинает новую сессию: для нового пути нужен новый `session_id`.

## Происхождение и отпечаток

Каждая строка `ledger` содержит ID собственной квитанции, `payment_event_id` и `source_event_ids` обязательных предшественников. `/api/receipts?event_id=...` возвращает оригинал и его повторы/конфликты, позволяя проверить время поступления и содержимое.

`source_event_ids` снимка — объединение событий, действительно участвующих в журнале, воронке или когортных значениях выбранного сегмента, включая необходимые предшественники. `context_event_ids` — остальная рассмотренная история до `end`: она нужна проектору для проверки цепочек и первой оплаты, но не объявляется вкладом в текущие показатели. Глобальные `quality`, `exclusions` и справочник `dimensions` имеют свою область.

Отпечаток включает политику, параметры периода/сегмента, показатели, воронку, когорты, дневные суммы и нормализованное содержимое contributing-событий. Он исключает номера квитанций, повторы, контекст, глобальные ошибки и саму метку `as_of`. Поэтому одинаковое бизнес-содержимое в разные моменты знания даёт одинаковый отпечаток; новая аренда в чужом канале не меняет отпечаток фильтрованного отчёта. Это не хеш всего HTTP-ответа: качество доставки может измениться при неизменных показателях.

`compare.added_event_ids` и `removed_event_ids` показывают изменение contributing-событий. Поздний предшественник и восстановленный им платёж попадают в добавленные источники; несвязанные события чужого сегмента — нет.

## Конкурентность и стоимость

Одна транзакция загрузки — один писатель. Для PostgreSQL используется advisory lock, для SQLite — немедленная транзакция. Второй процесс видит уже зафиксированную каноническую запись и классифицирует повтор. Триггеры запрещают изменение/удаление квитанций; приложение не предоставляет команд очистки.

Проекция сортирует историю событий, держит её в памяти и заново строит цепочки. Это прозрачный эталон семантики, не масштабируемая аналитическая платформа. Замеры должны указывать число доставок, движок, оборудование и методику; обещания о производительности без запуска не делаются.

## Экспорт

CSV рассчитывается заново по применённым фильтрам, а не выдаётся из сохранённого снимка панели. Новые доставки могут изменить результат; `X-Snapshot-Fingerprint` относится к экспортированному отчёту. Фиксированный `as_of` воспроизводим при неизменной истории, но лабораторный импорт с получением задним числом может изменить и такой срез. Хранилища неизменяемых материализованных снимков здесь нет.

## Объяснение пересмотра

`compare` один раз читает историю до `after` и строит оба среза из этого набора. Новая историческая доставка, поступившая между внутренними расчётами, не смешивает состояния базы.

`revision.ledger_changes` сопоставляет строки по `event_id`: added, removed, changed. Отсутствующая сторона равна нулю. Для суммы a денежный вектор равен `(max(a,0), max(-a,0), a)` — оплаты, положительная величина отмен, чистая стоимость. Вклад равен вектору после минус вектор до. `ledger_delta` суммирует вклады и совпадает с общей разницей трёх показателей.

Изменение состава может дать нулевую чистую разницу. Например, более ранняя оплата 7000 заменяет ранее учитывавшуюся 10000, а отмена перепривязывается с -10000 на -7000: изменение оплат -3000, отмен -3000, чистой стоимости 0. Удаление строки из проекции не означает удаление исходного события.

Каждая существующая сторона имеет `source_refs` канонических принятых квитанций: event_id, receipt_id, event_type, occurred_at, received_at, source. Повторы и конфликты не заменяют эти ссылки. `evidence` содержит факт известности собственной квитанции, прежнюю/новую причину исключения и изменения источников.

Причины `new_delivery`, `chain_became_valid`, `payment_relinked`, `provenance_changed`, `semantic_reclassification` определены в [контракте этапа](REVISION_PLAN.md). Это объяснение того, как пересчитался журнал, а не вывод о мотивах клиента или неисправности внешней системы.

`revision.funnel_changes` отдельно показывает число сессий, добавленные/исключённые/изменившиеся сессии и источники до/после. Такой пересмотр может не иметь денежного эффекта. Объяснения когорт в этот контракт не входят; их значения доступны в двух обычных снимках.
