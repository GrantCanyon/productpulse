# Этап 2: объяснение ревизии двух моментов знания

Контракт одобрен тимлидом после независимой матрицы QA. Базовая версия: `f3a5866` (код `2b2676f`).

## Результат

Сравнение двух `as_of` объясняет точный состав изменения денег, а не только показывает разность итогов. Существующие `before`, `after`, `delta`, `added_event_ids`, `removed_event_ids` сохраняются. Добавляется `revision`.

`revision.ledger_changes`: список по стабильному `event_id`. Каждая запись содержит:

- `change`: `added`, `removed` или `changed`;
- `operation_type`: `payment` либо `cancellation`;
- `before` и `after`: строка журнала или null, включая `payment_event_id` и `source_refs` (event_id, receipt_id, event_type, occurred_at, received_at, source);
- `contribution`: точная разница `gross_cents`, `reversed_cents`, `net_cents`;
- `reason` и `evidence`: причина, выводимая из двух срезов, прежнее/новое семантическое исключение и факт наличия собственной принятой квитанции.

Для суммы строки `a`: gross=max(a,0), reversed=max(-a,0), net=a. Вклад изменения равен значению после минус значение до; null равен нулю. `revision.ledger_delta` — сумма вкладов, обязана совпадать с соответствующими тремя полями общей `delta`. Нулевой net при изменившихся gross/reversed и составе строк показывается явно.

## Причины без предположений

- `new_delivery`: собственная принятая квитанция события отсутствует в раннем срезе и есть в позднем.
- `chain_became_valid`: событие было принято, исключалось как `missing_predecessor`, а теперь вошло в журнал.
- `payment_relinked`: у той же отмены действительно изменился `payment_event_id`.
- `provenance_changed`: денежная операция и сумма сохранились, но изменилась цепочка источников.
- `semantic_reclassification`: остальные подтверждённые изменения с прежней/новой причиной исключения. Нейтральный вариант, когда конкретную причину нельзя доказать.

Отмена — тип операции, а не догадка о причине поздней доставки. Фактические бизнес-мотивы клиента не выводятся из событий.

## Согласованность и область

Оба среза строятся из **одного прочитанного набора квитанций** до `after`; `before <= after` проверяется до чтения. Это предотвращает смешивание разных состояний базы при параллельном импорте задним числом.

Фильтры периода/сегмента одинаковы. События чужого сегмента не получают денежный вклад. Изменение только цепочки отражается с нулевым вкладом. Предшественники оплаты/отмены доступны в источниках до/после, включая оплату до начала периода.

`revision.funnel_changes` отдельно показывает этап, значения сессий до/после, добавленные/исключённые сессии и их источники. Изменение воронки без денег не объявляется причиной изменения выручки. Объяснения когорт в этот этап не входят. Семантика и отпечаток обычного отчёта не меняются ради нового объяснения: внутренние сведения о сессиях воронки не добавляются в публичный снимок.

## План и проверки

1. Ручные RED-сценарии: новая оплата; позднее восстановление принятой оплаты; отмена оплаты предыдущего периода; замена оплаты 10000 на ранее датированную 7000 с перепривязкой отмены (grossΔ=-3000, reversedΔ=-3000, netΔ=0); смена только источника; изменение только воронки; чужой сегмент; обратный диапазон; параллельная историческая доставка между чтениями.
2. Выделить внутренний проектор над фиксированным набором квитанций. Публичный отчёт сохраняет прежнюю форму. Рассчитать объяснение по фактам, проверить арифметическую сверку.
3. Панель: три суммы изменения раздельно, таблица строк с вкладом и доказательной причиной, просмотр источников до/после, отдельный блок воронки, ясное пустое состояние.
4. Набор SQLite/PostgreSQL, HTTP-контракт, линтер, синтаксис JS, независимое QA и UI-ревью. Обновить русское руководство и записать проверенный коммит.
