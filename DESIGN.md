# ProductPulse: контракт реализации

ProductPulse — синтетическая лаборатория аналитики аренды оборудования. Главный вопрос: **что было известно в выбранный момент и какие исходные события изменили показатели?** Реальных клиентов, персональных данных и заявлений о промышленном использовании нет.

## Архитектура

Python 3.12, SQLAlchemy 2, PostgreSQL — основная база; SQLite запускает ту же семантику без сервиса. FastAPI предоставляет панель и API только для чтения. Загрузка принадлежит CLI. Все ресурсы панели локальные. Аутентификации, браузерной записи и настроенных внешних отправителей телеметрии нет. Проектор выполняется в одном процессе: приоритет — проверяемость, не масштаб хранилища данных.

Квитанции добавляются без изменения старых строк: исходный JSON, SHA-256, источник, время получения, классификация, причина. `event_id` глобально уникален среди принятых событий. Эквивалентный повтор — `duplicate`; другое содержимое под существующим ID — `conflict`. Побеждает первая принятая доставка. Параллельная загрузка сериализуется транзакционной advisory-блокировкой PostgreSQL либо `BEGIN IMMEDIATE` SQLite; частичный уникальный индекс страхует каноническую идентичность. Триггеры запрещают UPDATE/DELETE квитанций обычными командами приложения.

## Две оси времени

- `occurred_at`: время бизнес-события; `[start,end)` — отчётный интервал.
- `received_at`: время доставки; `as_of` включает квитанции с `received_at <= as_of`.
- Эти фильтры независимы: известное заранее событие с датой позже `as_of` не отсекается. Дата события проверяется только по `end` при проекции и `[start,end)` при расчёте показателей.
- В демонстрации пользователь может задать историческое время получения. В реальной интеграции его обязан назначать доверенный серверный источник времени. Это не защищённый журнал времени внешней системы.

## Бизнес-семантика

Путь: `viewed → quoted → reserved → paid → cancelled`. Одна сессия принадлежит одному пользователю, аренде, каналу и категории. Порядок времени неубывающий; при одинаковой временной метке порядок этапов задаётся политикой, затем `event_id`. Проверка цепочки выполняется при чтении, поэтому поздний предшественник может восстановить ранее исключённый платёж.

Для аренды учитываются максимум одна оплата и одна полная отмена. Суммы — целые центы USD. Отмена уменьшает показатель в дату отмены, даже если оплата была до начала периода. Возврат частичной суммы не поддерживается.

Воронка считает уникальные сессии с первым действительным просмотром в `[start,end)` и этапами до `end`. Когорты определяются первой действительной оплатой пользователя за всю известную историю, а не первой оплатой после начала фильтра. Возврат в следующую неделю означает другую оплаченную аренду; отмена не стирает факт активности. Неделя начинается в понедельник UTC.

`observed` и `mature` определяются относительно `report.end`: началась ли неделя и завершилась ли она целиком. Это календарная наблюдаемость, а не гарантия полноты доставок. Ненаблюдаемые недели — `null`; текущая неполная неделя маркируется отдельно.

Оплаченные аренды и чистая стоимость бронирований — продуктовые показатели, **не бухгалтерская выручка**.

## Аудит и ограничения

Снимок содержит версию политики, детерминированный отпечаток, ссылки на события, журнал оплат и отмен, воронку, когорты, качество доставок и семантические исключения. Сравнение восстанавливает два момента знания. Некорректный JSON и схема — карантин; отсутствующий предшественник — пересчитываемое исключение.

Нет аутентификации, промышленного развёртывания, потоковой платформы, произвольных валют, частичных возвратов, склейки идентичности между устройствами, налогового учёта и заявлений о масштабе. Панель по умолчанию слушает только `127.0.0.1`. Исходные квитанции доступны через API: в демонстрацию нельзя загружать персональные данные.

## Порядок выполнения и проверки

1. Ручные сценарии повтора, конфликта, позднего предшественника, временных границ, отмен, когорт и происхождения. Сначала наблюдать сбой теста.
2. Хранилище, валидация, неизменяемые доставки, проектор и отчёт. Интеграционные проверки SQLite.
3. Детерминированный симулятор с независимым контрольным журналом; сверка, CLI, сравнение и JSON/CSV.
4. HTTP-контракт, панель с фильтрами, сравнением, очередью качества и просмотром цепочки источников.
5. Проверка паритета PostgreSQL, CI, SQL-рецепты, контейнеры, русское руководство. Полный набор тестов, линтер, реальные команды и визуальное ревью.

Фокус ревью: плохая строка не отменяет хорошие соседние; будущая доставка не попадает в прошлое знание; повтор не удваивает стоимость; отмены пересекают отчётные окна; неизвестное удержание не маскируется нулём; одновременные повторы сохраняют одну каноническую идентичность.
